# 开发流程

## 角色

### 主对话

- 冻结架构和接口。
- 发布一个功能一个 Issue。
- 指定 base commit、依赖、验收条件和文件所有权。
- 审查 Draft PR、CI、风险和合并顺序。
- 负责阶段验收，不承担普通功能实现。
- 定期检查所有运行中的子对话；不能把“已派发”当成“正在推进”。
- 多个子对话同时汇报时先排队，再逐项审查、反馈和验收，避免交叉修改审查结论。
- 子对话无文件、测试或 Git 进展且未响应状态检查时，中断并用可触发新轮次的 follow-up
  恢复；普通消息只传递信息，不保证已完成或中断的子对话重新工作。

### 实施子对话

- 使用独立 worktree。
- 创建 `codex/<issue>` 分支。
- 只实现当前 Issue。
- 编写和运行测试。
- commit、push 并创建 Draft PR。
- 根据 Review 修改；不得自行合并。
- 完成、测试失败、权限阻塞、异常停止或等待主审时必须主动向主对话汇报。
- 汇报必须包含当前 milestone、修改路径、执行命令、测试计数、跳过项、Git 状态和阻塞原因。

## Issue 必填

```text
baseCommit
objective
nonGoals
ownedPaths
frozenContracts
dependencies
acceptanceTests
requiredChecks
demoEvidence
stopConditions
mergeOrder
```

## PR 门

- 变更与 Issue 一致。
- 没有复制未审查的 V1 代码。
- 单元测试覆盖成功和失败。
- 跨模块能力有集成或 E2E 测试。
- 报告精确测试命令、跳过项、原因和风险。
- 主对话完成静态审查。
- 主对话按固定 head SHA 审查精确文件清单、越界路径、生成物、密钥/`.env`、测试专用依赖
  和权威边界；子对话自审不能替代主审。
- CI 必须对应被审查的 fixed head 且全部成功。新的提交会使先前审查和 CI 失效，必须重跑。
- 子对话只创建 Draft PR；只有主对话可以转 Ready、合并、更新下游 base 和发布阶段验收。

## 并行规则

- 契约未冻结前不并行实现依赖它的功能。
- 并行 PR 不应修改同一核心文件。
- 同时维护的实现 PR 初期不超过 4 个。
- 共享接口只能由指定 Owner PR 修改。
- 合并后，下游分支及时更新 base。

## 用户验收

用户验收用于确认真实体验，不应承担第一轮发现基础集成错误。进入用户验收前必须已有自动化端到端旅程。

真实用户旅程应尽量覆盖“注册或登录 -> 输入问题 -> Runtime 执行 -> 返回结果 -> 检查事件、
receipt、diff 和失败恢复”。但在 API、Web UI 和真实 Provider 尚未实现前，不得伪造该验收
已完成。密钥只能通过明确设计的 ExecutionProfile/测试注入边界使用；开发者和 Agent 不读取、
复制、提交或输出 `.env`。

## 状态检查与硬阻塞

主对话在有运行中子对话时持续轮询，并在每个 milestone 后进行静态、行为和边界审查。发现
问题后只把明确修改意见发回对应子对话，修复完成后重新审查 fixed head。

只有以下三类情况允许等待用户决定：

1. 缺少会改变产品行为或架构边界的必要决策。
2. 需要用户身份、权限、OAuth、OTP 或无法由当前授权完成的认证。
3. 需要扩大成本、生产范围，或执行不可逆/高风险操作。

测试失败、实现困难、审查意见或可恢复的工具异常不是硬阻塞；应记录证据、尝试安全替代并
继续推进。

## 安全停止与交接

用户要求暂停或额度接近上限时：

1. 不再启动新功能，把当前工作推进到最近的可恢复点（通常是干净提交和 Draft PR）。
2. 不为赶进度跳过测试、主审或 CI，也不擅自合并。
3. 更新 `docs/ACTIVE_DEVELOPMENT.md`，记录准确 SHA、Issue/PR、worktree、测试、风险、下一
   动作和禁止动作。
4. 用只读 Git/GitHub 命令复核文档事实，并执行一次无聊天上下文的冷启动检查。
5. 明确向用户报告停止位置，然后停止。
